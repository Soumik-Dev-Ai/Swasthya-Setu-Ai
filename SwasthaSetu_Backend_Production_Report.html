Swasthya Setu AI ?" Backend Production Report

This document serves as the authoritative production architecture reference for the Swasthya Setu AI backend. It details exactly how the API layer functions, the AI integration strategies, database configurations, and failover mechanisms.

1. High-Level Architecture

  • Framework: FastAPI (Python 3.12+)
  • Concurrency: Fully asynchronous (async def) ensuring non-blocking operations for heavy I/O tasks like AI inference and web scraping.
  • Data Validation: Strict boundary enforcement using Pydantic v2 schemas (located in app/schemas/). Invalid client payloads or corrupted LLM JSON strings are instantly rejected with HTTP 422, preventing internal server (500) crashes.
  • Entrypoint: app/main.py
  • Routing: API endpoints are mounted via app/api/routers/v2_engine.py.

2. Database & State Management

Swasthya Setu AI was explicitly designed to be deployed in low-resource or testing environments with zero devops overhead. - Engine: Uses a local SQLite file (swasthyasetu.db) powered by aiosqlite for async concurrency. - Auto-Provisioning: The backend checks the DATABASE_URL during the startup event. If it detects a sqlite string, it automatically creates the necessary tables using SQLAlchemy's Base.metadata.create_all. - Production Scaling: If hosted on a cloud provider like AWS, the system can instantly switch to PostgreSQL simply by changing the DATABASE_URL in the .env file (e.g., postgresql+asyncpg://...) and running Alembic migrations (alembic upgrade head).

3. The AI Vision Cascade (Triage Module)

The backend features a highly resilient, fault-tolerant Vision LLM pipeline designed to never leave a patient stranded. - File: app/services/vision_service.py - Provider Cascade: 1. gemini/gemini-1.5-flash (Primary) 2. groq/llama-3.2-90b-vision-preview (Fallback 1) 3. nvidia/llama-3.1-70b-instruct (Fallback 2) - Library: Powered by litellm which handles unified prompt translation and routing. - Security Guardrails: Images are strictly checked before they reach the AI. Max size is 8MB (VISION_MAX_IMAGE_BYTES), and MIME types are whitelisted to image/jpeg, image/png, image/webp. - Fail-Safe Mechanism: If every provider in the cascade hits rate limits or times out, the system catches the exception and returns a dummy uncertain signal (confidence: 0). The core Deterministic Safety Gate will then evaluate the text symptoms on its own.

4. Precision OSINT Scraper (Cost Engine)

To prevent the AI from hallucinating treatment costs, the backend implements a real-time web scraper. - File: app/services/precision_service.py - Scraper: Uses duckduckgo_search (DDGS) to perform targeted OSINT queries. - Target Boundaries: Queries are strictly confined using site:nih.gov OR site:who.int OR site:mayoclinic.org to ensure only peer-reviewed medical pricing and data are injected. - Strict Latency Limits: The entire scrape is wrapped in an asyncio.wait_for timeout strictly capped at 3.5 seconds. If the network stalls, the backend aborts the scrape, swallows the error, and returns empty arrays so the frontend can seamlessly render its offline-first local estimates without delaying the user.

5. Security & Rate Limiting

  • CORS: Handled by FastAPI's CORSMiddleware. Allowed origins are configured in settings.CORS_ORIGINS (defaults to Vite's local ports 5173).
  • Rate Limiting: Protects the advanced AI endpoints (e.g., /facilities/advanced-search) using slowapi. Currently throttled at 10 requests per minute per IP (ADVANCED_SEARCH_RATE_LIMIT) to prevent malicious token draining on your paid AI accounts.

6. Environment Configuration (.env)

The backend strictly relies on the .env file (loaded via pydantic-settings). Keys are NEVER hardcoded in the repository. - GEMINI_API_KEY, GROQ_API_KEY, NVIDIA_API_KEY - GOOGLE_MAPS_API_KEY (Optional; frontend falls back to Pigeon Maps / SVG if missing). - ENABLE_WEB_SCRAPE=True (Feature toggle for the OSINT precision scraper).

End of Report. The backend is verified stable, strictly bounded by Pydantic, and cleared for live production usage.
